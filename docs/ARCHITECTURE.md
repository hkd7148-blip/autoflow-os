# Архитектура AUTOFLOW OS

## Обзор системы

AUTOFLOW OS построен на модульной микросервисной архитектуре, где каждый компонент отвечает за свою область бизнес-логики и может масштабироваться независимо.

## Компоненты системы

### 1. Telegram Bot (Aiogram 3)

Основной интерфейс взаимодействия с пользователями.

**Структура:**
```
src/bot/
├── main.py              # Точка входа, инициализация
├── handlers/            # Обработчики команд
│   ├── client.py        # Хендлеры для клиентов
│   ├── manager.py       # Хендлеры для менеджеров
│   ├── mechanic.py      # Хендлеры для механиков
│   └── admin.py         # Административные команды
├── keyboards/           # Генераторы клавиатур
│   ├── client.py        # Клавиатуры клиента
│   ├── manager.py       # Клавиатуры менеджера
│   └── mechanic.py      # Клавиатуры механика
├── middlewares/         # Промежуточные обработчики
│   ├── auth.py          # Авторизация и роли
│   └── logging.py       # Логирование запросов
└── states/              # FSM состояния диалогов
    └── booking.py       # Состояния записи на сервис
```

**Ключевые особенности:**
- Асинхронная обработка сообщений
- FSM для многошаговых диалогов
- Redis Storage для персистентности состояний
- Ролевая модель доступа (client/manager/mechanic/admin)

---

### 2. REST API (FastAPI)

Внешний API для интеграций и веб-интерфейса.

**Структура:**
```
src/api/
├── main.py              # FastAPI приложение
├── routes/              # Эндпоинты
│   ├── clients.py       # CRUD клиентов
│   ├── orders.py        # Работа с заказами
│   ├── parts.py         # Запчасти и склад
│   └── analytics.py     # Отчёты и статистика
├── models/              # Pydantic модели
│   ├── client.py
│   ├── order.py
│   └── part.py
└── dependencies/        # Зависимости FastAPI
    ├── auth.py          # JWT аутентификация
    └── database.py      # Сессии БД
```

**Эндпоинты:**
- `GET /api/v1/clients` — список клиентов
- `GET /api/v1/clients/{id}` — карточка клиента
- `POST /api/v1/orders` — создание заказа
- `GET /api/v1/parts/search` — поиск запчастей
- `GET /api/v1/analytics/dashboard` — данные для дашборда

### 3. Бизнес-модули

#### RECEPTION — Модуль приёма

**Ответственность:**
- Квалификация входящих обращений
- Сбор информации о проблеме
- Бронирование слотов
- Создание предварительных заказ-нарядов

**Взаимодействие:**
```
Клиент → Bot Handler → ReceptionService → 1C API
                                       → PostgreSQL
                                       → SMS Gateway
```

#### CRM — Модуль управления клиентами

**Ответственность:**
- Поиск и отображение карточек клиентов
- История взаимодействий
- Управление автопарком
- Взаиморасчёты и баланс

**Взаимодействие:**
```
Менеджер → Bot Handler → CRMService → PostgreSQL
                                    → 1C API (sync)
```

#### WAREHOUSE — Модуль склада

**Ответственность:**
- Поиск запчастей по артикулу/названию
- Отображение остатков
- Подбор аналогов (кросс-референс)
- Резервирование под заказ

**Взаимодействие:**
```
Механик → Bot Handler → WarehouseService → PostgreSQL
                                         → 1C API (realtime)
```

#### BRAIN — AI-модуль диагностики

**Ответственность:**
- Расшифровка кодов ошибок OBD/DTC
- Анализ симптомов неисправностей
- Рекомендации по диагностике
- Поиск по базе знаний

**Архитектура RAG:**
```
┌─────────────────────────────────────────────────────────────┐
│                      BRAIN Module                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌─────────┐    ┌─────────────┐    ┌─────────────────────┐ │
│  │ Запрос  │───▶│  Embedding  │───▶│   Similarity Search │ │
│  │механика │    │  (OpenAI)   │    │     (ChromaDB)      │ │
│  └─────────┘    └─────────────┘    └──────────┬──────────┘ │
│                                               │            │
│                                               ▼            │
│  ┌─────────┐    ┌─────────────┐    ┌─────────────────────┐ │
│  │  Ответ  │◀───│     LLM     │◀───│  Релевантные доки   │ │
│  │   AI    │    │(Claude/GPT) │    │   + контекст        │ │
│  └─────────┘    └─────────────┘    └─────────────────────┘ │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4. Слой данных

#### PostgreSQL — Основная БД

**Схема данных:**
```sql
-- Клиенты
clients (id, name, phone, email, inn, client_type, created_at)

-- Автопарк
vehicles (id, client_id, brand, model, year, vin, plate_number)

-- Заказы
orders (id, client_id, vehicle_id, status, problem, created_at)

-- Запчасти
parts (id, article, name, brand, price, quantity)

-- Пользователи бота
bot_users (id, telegram_id, role, client_id, created_at)
```

#### Redis — Кэш и сессии

**Использование:**
- FSM состояния диалогов
- Кэш карточек клиентов (TTL: 5 мин)
- Кэш остатков запчастей (TTL: 1 мин)
- Rate limiting

#### ChromaDB — Векторная БД

**Коллекции:**
- `repair_knowledge` — база знаний по ремонту
- `error_codes` — коды ошибок и расшифровки
- `service_history` — история ремонтов для обучения

---

### 5. Интеграции

#### 1С:Предприятие

**Тип интеграции:** REST API (HTTP Services)

**Синхронизируемые данные:**
- Клиенты и контрагенты
- Автомобили
- Заказ-наряды
- Остатки запчастей
- Цены

**Режимы синхронизации:**
- Real-time: остатки, создание заказов
- Периодическая (5 мин): клиенты, цены
- По запросу: полная синхронизация

#### SMS Gateway

**Провайдер:** SMS.ru / SMSC.ru

**Триггеры отправки:**
- Подтверждение записи
- Напоминание за 1 час
- Готовность автомобиля
- Акции и спецпредложения

## Потоки данных

### Сценарий: Запись клиента на сервис

```
1. Клиент отправляет сообщение в Telegram
                    │
                    ▼
2. Aiogram получает Update, вызывает Handler
                    │
                    ▼
3. AuthMiddleware проверяет/создаёт пользователя
                    │
                    ▼
4. FSM переводит в состояние "сбор данных"
                    │
                    ▼
5. После сбора данных → ReceptionService.create_booking()
                    │
                    ├──▶ Сохранение в PostgreSQL
                    │
                    ├──▶ Создание записи в 1С (API)
                    │
                    └──▶ Отправка SMS-подтверждения
                    │
                    ▼
6. Ответ клиенту с номером заказ-наряда
```

### Сценарий: AI-диагностика

```
1. Механик вводит код ошибки P0087
                    │
                    ▼
2. BrainService.analyze_error_code("P0087")
                    │
                    ├──▶ Проверка в локальной базе кодов
                    │
                    ├──▶ Поиск в ChromaDB (похожие случаи)
                    │
                    └──▶ Запрос к LLM с контекстом
                    │
                    ▼
3. Формирование ответа с вероятностями причин
                    │
                    ▼
4. Отправка результата механику
```

## Безопасность

### Аутентификация

- **Telegram:** Проверка telegram_id, роли в БД
- **API:** JWT токены (access + refresh)
- **1С:** API Token в заголовках

### Авторизация

**Ролевая модель:**
| Роль | Доступные модули |
|------|------------------|
| client | RECEPTION (свои заказы) |
| manager | RECEPTION, CRM, ANALYTICS |
| mechanic | WAREHOUSE, BRAIN |
| admin | Все модули + настройки |

### Защита данных

- Шифрование паролей: bcrypt
- HTTPS для всех внешних соединений
- Валидация входных данных: Pydantic
- SQL Injection защита: SQLAlchemy ORM
- Rate limiting: Redis-based

## Мониторинг

### Метрики

- Количество активных пользователей
- Время ответа бота
- Количество заказов в час
- Точность AI-диагностики
- Ошибки интеграции с 1С

### Логирование

- Уровни: DEBUG, INFO, WARNING, ERROR
- Формат: JSON (для ELK Stack)
- Ротация: ежедневно, хранение 30 дней

### Алерты

- Бот не отвечает > 1 мин
- Ошибки 1С синхронизации
- Высокая нагрузка на БД
- Исчерпание лимитов API (OpenAI)
